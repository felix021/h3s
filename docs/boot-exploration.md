# 应用入口启动探索：第一轮

2026-11-10，从官方 0.1.1.8 的应用入口 `0x06000100` 做了五组独立、有指令预算的离线试跑。**尚未启动 H3S：已定位到 PLL 状态、ROM 函数和启动参数三类具体依赖。** 最远的一组执行了 13 条指令后进入未映射 ROM；还没有到 BSS 清零、数据复制、RTOS 或蓝牙初始化。

工具：[tools/probe_boot.py](../tools/probe_boot.py)。完整脱敏结果：[evidence/boot-exploration.json](../evidence/boot-exploration.json)。真实固件指令摘录：[evidence/boot-entry.asm](../evidence/boot-entry.asm)。这轮没有操作设备或生成固件，耳机继续使用已恢复、已验收的 b79 ANC 镜像。

## 如何复现

Python3.11+、Git，使用与 [函数级探针](preflash-emulation.md) 相同的固定模拟器提交，不需要 GPU、厂商编译器或私有 Flash 备份：

```bash
python3 tools/fetch_firmware.py --variant original
python3 tools/probe_boot.py --fetch-simulator --check-known-blockers \
  --report analysis/boot-exploration/round1.json
```

原包 SHA256 固定为 `65cafc7f9a7545c5c30701d141c77db334e37065589e42c51306132c94c879af`，解出的 842654B 应用固定为 `18f3d573a5b1a15f488a6803ce4f828634e602015c85e92d205bbe62d7060041`。当前修改版 UFW 不作为该工具的输入。

每组默认最多 100000 次 step，可用 `--max-steps` 降低，硬上限为1000000。每次未知读取／取指或不支持指令立即停止；不会在失败的 CPU 上跳过该指令续跑。保留最后64条指令以及内存事件、适配器计数和寄存器。`--check-known-blockers` 检查本轮五个精确停止点、指令数、栈深度、写入的两项时钟值及 R0 恢复；退出0表示预期回归通过，**不表示启动成功或允许刷机**。

## 五组试跑结果

| 场景 | 已完成 step | 停止位置 | 原因 |
| --- | ---: | --- | --- |
| 未加启动指令适配 | 0 | `0x06000100` | 上游 `li.sr_u32` 模型依赖硬件测试记录上下文，缺少 `id` |
| 只适配入口 SP／SSP 两次赋值 | 6 | `0x0603561e` | 读取未建模的 `0x00fd4600`，参考 SDK 对应 `JL_PLL0.CON0` |
| 上述适配 + 假设 PLL 寄存器=0 | 11 | `0x06035636` | 上游双字存储模型为了合并／筛选写入而读取旧 RAM，触发未初始化读取；这是模型的记账操作 |
| 再适配这一条完整8B存储 | 13 | `0x0001fe14` | 跳入未映射 ROM；参考 SDK 符号为 `_pll_init` |
| 假设 PLL 寄存器=1、入口 R0=`0x0019fc28` | 11 | `0x060664d8` | 真正读取启动参数 `R0+4`，但内容未知；以未初始化内存拒绝 |

这些是各自从入口重新开始的路径，不能把 step 数相加当成一次连续启动。PLL=0/1、R0 候选指针均是**诊断假设，不是设备读值或已复原的 boot handoff**。该两种 PLL 取值只探索 bit0 分支，不穷举其他状态。

## 实际控制流说明了什么

应用开头依次设置 SP 和 SSP 为 `0x00123840`，保存 `{r2-r0}`，调用 `0x06035616`。该函数保存返回地址后读取 `0x00fd4600`：

- bit0为1时跳到函数返回，随后恢复入口 r0/r1/r2，调用 `0x060664d8`。
- bit0为0时，把 24000000、48000000 写到 `0x0019fc2c`、`0x0019fc30`，然后调用 `0x0001fe14`。

参考 SDK 把 `0x0019fc28` 命名为 `boot_arg_list`，把 `0x0001fe14` 命名为 `_pll_init`。实际 QCY 指令对这些地址的使用能核对这一解释，但**尚未确认该 ROM 修订版的实现、调用约定或真实初始寄存器值**。

`0x060664d8` 从入口保留的 R0 读取偏移4、8，再读偏移0处的指针并解引用；后续还访问偏移12、14、16、20。这说明启动交接至少需要这些字段及内嵌指针所指对象，不能只填一个入口 PC。上述 R0 候选值来自参考符号和 QCY 对该对象附近的写入，尚无真实交接状态验证。私有的2MiB备份是外部 Flash，不提供内部 ROM 和启动时 RAM 的内容。

供参考的源码来自固定 JL701N SDK 提交 `67328f4741c69993c88e504c67377b196c724f97`（[来源仓库](https://gitlab.zh-jieli.com/ai_test/701n)）；它不是 QCY 的确切源码。此次核对文件的摘要：

| 文件 | SHA256 |
| --- | --- |
| `br28.h` | `111e29ea8d3d72e504a221caf035552250dcda959d4b79e8e1cd13623a6aad01` |
| `maskrom_stubs.ld` | `331e973cbd71d5f9add4b77a796036f88e8dad93f940b70bb82398b7748a4547` |

`br28.h` 中 `ls_base=0xfd0000`，`map_adr(grp,adr)=(64*grp+adr)*4`，PLL0 group=0x46，首项 CON0，所以地址为0xfd4600。完整参考文件没有在此次提交中重新发布。

## 模型适配与初始条件

第一组保留原执行器的失败；后续两类局部适配都明确计数，不修改下载的上游代码：

1. 仅对入口两条精确匹配的 `li.sr_u32` 设置 SP／SSP 可见值。不模拟运行模式切换、栈银行或中断。
2. 仅对 `0x06035636` 的精确 `st.d.l` 做完整8B写入，保持寄存器和 flags。上游 `semantics/m2.py:Writes` 即使对完整字存储，也会读取旧值来合并字节、过滤未改变的写入；不能把这种模拟器内部读取当作真实 CPU 的 RAM 依赖，更不能因此把所有未知 RAM 填0。

RAM 使用逐字节初始化跟踪，仅开放入口栈的一个有界窗口和24B候选交接对象；这是探针的范围选择，不是完整芯片内存图。SP设置前的寄存器、flags、SP、RETS、ICFG以0占位，明确标为未测量状态；诊断组单独覆盖 R0。未写过的 RAM 不会自动返回0，PLL之外没有外设寄存器返回假值，也没有 ROM API 桩。没有真实异常控制器、PC保护寄存器或双核模型。

## 这一轮收敛出的下一步

先解决启动交接和早期 PLL 路径，比直接补蓝牙模型更有收益：

1. 从参考 loader／启动源码与真实 QCY 指令交叉还原 R0 指向的对象、内嵌指针和必要字段；区分能从 UFW／Flash 导出的常量与仍缺少的运行状态。
2. 核对 PLL0 bit0 的实际语义、应用交接前的值、`_pll_init` 参数及副作用。可选择有依据地模拟该 ROM 函数，或重建 loader 已完成初始化的交接场景；不能仅靠假返回让程序向前跑。
3. 通过上述关口后，再推进 BSS／data／RAM代码复制和早期中断配置，检查实际覆盖的范围。当前执行器的 `rep` 等仍有测试场景限定，不能直接用于任意启动循环。
4. 用新到达的停止点决定时钟、定时器、异常和 RTOS 模型的最小范围，再估计到主循环的工作量。

当前可以确认“应用入口很早就依赖硬件和交接状态”；不能据13条已执行指令推算完成百分比、声称启动接近成功，或证明这就是历史 r2 在实机上的唯一异常位置。
