# 仿真器性能/内存预算分析（路 PERF / sim-perf，2026-11-15）

只读预研路：**零 tools/ 改动**（测量脚本在 `~/tmp/perf-prof/`，长跑日志/数据不进仓）。
回答用户关切原话——「16gb也太大了 模拟器用的什么语言性能这么差?」——用实测分解代替
印象，并给 S19/D1/L2 前瞻的预算外推与优化选项分级。

- 基线：main `b592ecc`（worktree `sim-perf`，本路无代码改动）。
- 对象：条件前沿场景 `p11_heap_experimental`（flag 集单源 `frontier_registry`，经
  `analyze_image_trace.frontier_run` 跑 official 单臂——与 L2 差分完全同一调用链，只差
  第二镜像；事件时钟/交付投影全开，是最重配置）。
- 红线遵守：一切结论基于实测；外推明确标「外推」；测量数字带环境。

## 1. 测量环境与方法

| 项 | 值 |

| Python | 3.12.3（CPython 系统解释器） |

## 2. 时间热点分解

### 2.1 总量（干净 20M 长程，单臂）

| 指标 | 实测 |
|---|---|
| 墙钟 | **1288.6s（21.5 分钟）**，19,996,266 步 |
| 平均速率 | **15,518 步/s**（64.5µs/步，含事件时钟段摊入） |
| 纯步进段峰值速率 | ~17,900 步/s（55.9µs/步，t=841-961 窗实测） |
| 事件时钟推进量 | 13,429,113 次虚拟 advance（与 DT 一致） |
| 事件时钟单位成本 | 估 ~10.8µs/次（总墙钟 − 20M×55.9µs ≈ 146s ÷ 13.43M，**推算值**） |

20M 窗内速率在 11.4k..17.9k 步/s 间波动：低速窗=OS 等待族（事件时钟逐虚拟步推进，
trace 不增长）；高速窗=纯 CPU0 忙等/执行段。

### 2.2 步进段类别占比（py-spy 200Hz×45s，自耗时）

| 类别（按文件归属） | 自耗时占比 | 内容 |
|---|---|---|
| A 主循环+CPU 壳+Memory 读写（probe_boot.py） | **37.8%** | Memory.read 逐字节 dict 装配+region 线性扫、step() 诊断链、主循环 row 组装 |
| E 上游解码/执行/格式化（sim/check/codec/table.py） | **20.0%** | operands/field_bits（每次重建位串扫描）、codec.format 反汇编文本、State 构造 |
| G inspect 反射（inspect.py） | **13.8%** | `check.takes_state` **每次 effect() 调用 `inspect.signature(fn)`**（上游 check.py:106，纯重复计算） |
| C trace 签名（analyze_image_trace.py） | **12.8%** | after_step 每步 16 寄存器签名字符串化 + `sys.intern` |
| B 外设/advance 仲裁（br28_model.py） | **9.7%** | 每步 advance()：ICU/watchdog/双 core tick/Timer0/软件 pending 全扫描 + eligible 多次 |
| D 机器调度/簿记（br28_machine.py） | 3.4% | select 轮转、icfg_demands、after_step 簿记 |
| F 指令语义模型（semantics/*） | **1.1%** | 真正的指令语义 |
| H 抽象值对象（br28_icfg/unknown） | 0.6% | UnknownWord/IcfgValue 操作 |

**直接回答「性能这么差？」：真正的指令语义只占 ~1%；~85% 是每步脚手架**——逐字节
dict 内存装配（每次读 8+ 函数调用：require/mmu.translate/sfc 检查/三段范围扫描/
handles/read_bytes/region 线性扫/逐字节 genexpr）、每步 inspect.signature 反射、每步
反汇编文本生成（喂给只保留 64 行的诊断 trace，即刻丢弃）、每步 16 签名串化、每步 IRQ
仲裁全扫描。这是「正确性优先+全量簿记」架构的代价，不是 Python 语言本身的下限。

关键帧 cumulative（同窗）：`explore` 主循环 100%；`CPU.step`（壳）54.2%；上游
`sim.step` 35.0%；`after_step`（trace 签名）14.4%；`decode` 13.6%；`advance`（IRQ
仲裁）7.1%；`machine.select` 2.1%。

### 2.3 每步精确调用计数（计数 wrapper，200k 步，13.5k 步/s）

cProfile 在本负载下开销 ~500x（每步数百次微函数调用，实测降到 ~27 步/s）不可用；
改用零语义改动的计数 wrapper（开销 <6%）：

| 每模型步调用次数 | 计数 | 意义 |
|---|---|---|
| `codec.format`（反汇编文本） | **1.013** | 每步一次反汇编格式化，产出喂给只保留 64 行的诊断 trace——**即刻丢弃的纯开销**（pair() 的 half_mask 解析另有少量） |
| `check.operands` | **2.129** | 每步两次操作数提取（主循环投影链 + 上游 effect） |
| `check.takes_state` = `inspect.signature` | **0.881** | **每次 effect() 用 inspect.signature 反射模型函数签名**（上游 check.py:106）判断模型形态——结果按函数恒定，纯重复计算；py-spy 里 inspect 自耗时 13.8% |
| `BR28Model.advance` | 1.011 | 每步一次仲裁全扫（+事件时钟段额外推进） |
| `codec.decode` | 0.032 | **解码缓存有效**（命中率 ~97%），解码不是热点 |
| `IRQController.eligible` | 0.033（200k 窗） | 早期窗 IRQ 族大多未 pending；OS 等待段（3.2M-19.1M，20M 世界 13.43M 次事件时钟推进+2,354 次延期重检）密度更高——以 py-spy 长程 9.7%（advance 族）为准 |

### 2.4 IRQ 仲裁/事件时钟段形状

- 每个模型步后固定调一次 `BR28Model.advance()`：counts 计数、ICU、watchdog、双 core
  tick 循环（各含 unresolved/pending 分支的 `eligible()` 重检）、Timer0 advance+pending
  双核资格循环、软件 pending 2 核×4 位循环（`eligible()` 最多 8 次/步）+ Timer2。
  `eligible()` 本体极便宜（~6 行整数运算），贵在**每步全族重扫的固定开销**（类别 B
  9.7% 的大部分）。
- 事件时钟段：全核 IDLE 时逐虚拟步调**同一个** `advance()`（BI 契约「无跳步」是刻意
  的正确性选择），13.43M 次推进无解码/无签名/无 row，单位成本估 ~10.8µs（比全步
  55.9µs 便宜 5 倍）；20M 世界里事件时钟约占总墙钟 **~11%**（146s/1288.6s，推算）。

## 3. 内存去向分解（含生命周期分类）

### 3.1 顶部结论

20M 单臂峰值 **6.64GB（6,961,464kB）**，RSS-行数曲线**严格线性**，边际
**353 B/行**（与 DT 修复后 ~370B 估计一致）。双镜像 21.8M 全量差分 = 两臂相加 ≈
**15.5-16GB**（与 DT 实测 ~16GB 对上）。

### 3.2 每行 353B 的构成（200k 步世界深尺寸实测）

| 成分 | 字节/行 | 说明 |
|---|---|---|
| 外层 6 元组 | 88 B | (core, before_pc, pc, flags, 16 签名元组, writes 元组) |
| 内层 16 元组 | 168 B | 16 个寄存器签名字符串的容器 |
| 2 个 PC int | ~57 B | 每步新分配（值重复但对象不共享） |
| 签名字符串 | ≈0（摊销） | **intern 后唯一串池全 run 仅 1.64MB/33,364 串**（饱和，值高度重复）——DT 修复的收益就在这：修复前每步 16×~55B 新串 ≈ +880B/行 |
| 分配器余量 | ~40 B | pymalloc arena 开销 |

### 3.3 大项生命周期分类（用户追问：「16GB 里哪些是废弃/可丢弃信息」）

分类口径：①必须常驻（后续步骤随机访问）②只在终态聚合读一次（可流式聚合，保
计数+首末+具名片段即可）③已消费即死（比对/入报告后无任何未来读者）。

| 大项 | 单臂@20M 体积 | 类 | 未来读者是谁 / 丢法 |
|---|---|---|---|
| **trace 签名链（两臂）** | **7.07GB**（353B×20M） | **③** | 唯一消费者=终态 pair 比对（严格单遍 zip 顺序读）+报告嵌入的 ±6 行上下文/前 8 分歧段首行。比对后即死；无控制流分歧时 reconvergence 也不需要。**可流式对比/分段落盘，常驻只需计数+首末样本+分歧上下文** |
| timer0_irq_deliveries 逐条簿记 | 3,482 条@20M ≈ 5-7MB（运行时 ~1.5KB/条；SNAP 紧凑形态 2.2MB/2.36MB） | ② | 报告+check 断言只消费：计数、末条（reti_from/PRD）、首条、全量进报告 JSON（无人逐条再读）。**可聚合为计数+首末+抽样**；SNAP 快照体积同步缩 |
| core_tick/software 簿记 | 110+14 条 ≈ 0.2MB | ② | 同上 |
| milestones（watched PC 事件） | 23 条@200k（3.4KB），随 watch_pcs 命中线性 | ② | 报告全量进 JSON；check 断言取特定条目 |
| events/deferral 事件环 | 有界 32/64 条（12KB） | ①（有界） | 设计上有界，无需处理 |
| 世界状态：mem.ram 逐字节 dict | 54,899 字节项@200k ≈ 3.9MB（~71B/字节项，dict 形态胖） | ① | 当前世界，随机访问，必须常驻（形态可紧凑化但属实施细节） |
| decode 缓存（双核） | 5,126 项 ≈ 2.0MB | ①（可再导出） | memoization，语义透明可重建（SNAP 已论证排除） |
| 报告 JSON（result dict） | 151KB@200k（含 peripherals/快照摘要，@20M 约 MB 级） | ② | 终态一次写盘 |
| 事件时钟/适配器计数器 | Counter 若干 | ① | KB 级 |

**结论：~16GB 双镜像峰值里，③「已消费即死」的签名链占 >99.9%（15.5GB）；②「终态聚合
一次」簿记占 ~0.05%（5-10MB）；①「必须常驻」世界+缓存占 ~0.1%（<20MB，双世界
~40MB）。DT 的 intern 修复已经把签名链里的字符串冗余压干（30GB→16GB 正是砍掉
+880B/行的重复串分配）；剩余 353B/行全是元组骨架+PC int——「信息」本身（唯一签名值
+每步 PC 序列）在 50M 步也只有 GB 级的熵，常驻 35GB 是表示方式+生命周期管理问题，
不是信息量问题。**

### 3.4 分配归因方法说明（tracemalloc 取舍）

tracemalloc(8 帧) 试跑 300k 步实测开销与 cProfile 同量级（>100x，30 分钟未过半程），
对 20M 级长跑不可行，主动中止；分配侧归因改由「RSS-行数斜率（353B/行，20M 全程线性）
+ 200k 世界逐对象深尺寸抽样（§3.2/§3.3）」组合给出——两者在「trace 行占 >99.9% 增长」
上一致（353B×20M=7.07GB vs 其余大项合计 <20MB），无需逐行归因再证。要点：真正需要
tracemalloc 的场景是「增长归因不明」的长跑；本测量的增长全部落在单一构造点
（`analyze_image_trace.py:376` after_step 的行 append），代码级即可定位。

## 4. 50M 步外推预算表（外推，基于实测边际线性外推）

假设：步构成与 20M 世界同形（事件时钟占比不变）；双镜像=两臂 trace 同时常驻（现行
compare_pair 语义）；三镜像 L2-a=3 对×2 臂=6 次全前缀重放（现行 analyze_image_trace
不跨 pair 复用 run）。

### 4.1 内存（RAM 峰值；「回收」= §3.3 生命周期分类对应的丢弃/流式化）

| 场景（50M 步/臂） | 现状（全常驻） | 只回收③（签名链流式/spill） | 只回收②（簿记聚合） | 回收③+②（①为地板） |
|---|---|---|---|---|
| 单臂跑 | ~17.7GB | **~0.3GB**（世界+报告；可选 17.7GB 盘 spill） | ~17.7GB（省 MB 级，无感） | ~0.3GB |
| 双镜像差分 | **~35.4GB（本机 29GB 可用即 OOM）** | **~0.5GB** + ~17.7GB 盘（trace_a spill 流式比对；O4 打包后盘 ~3GB） | ~35.3GB（省 ~10MB，无感） | ~0.5GB |
| 三镜像 L2-a | 同双镜像（对间顺序） | ~0.5GB + 盘（2×17.7GB 顺序复用） | 同左 | 同左 |

②单独回收对 RAM 无感（MB 级），价值在**快照体积**（2.36MB→<0.2MB/份）与「无界
增长类清零」；③是唯一决定性项。①地板（世界五元组+缓存+报告，双世界）~40-60MB。
对照现状锚点：21.8M 双镜像 ≈16GB（DT 实测），与线性外推 35.4GB×(21.8/50) 一致。

### 4.2 时间（墙钟，15.5k 步/s 实测均值外推）

| 场景 | 现状 | O1+O2 后（~1.3x，CPU 低风险项） | 再 O3+O7 后（事件时钟段大部回收） |
|---|---|---|---|
| 单臂 50M | ~54 分钟 | ~41 分钟 | ~30-35 分钟（S19 形状事件时钟占 2/3 时收益更大，**外推**） |
| 双镜像 50M | ~1.8 小时 | ~1.4 小时 | ~1.0-1.2 小时 |
| 三镜像 L2-a | **~5.4 小时**（6 臂） | ~4.1 小时；**轨迹复用改 3 臂后 ~2.1 小时**（codex 问题 1/2 范畴） | ~1.5-2.5 小时 |

## 5. 优化选项分级（ROI 排序；全部未实施，归实施路一案一 PR）

ROI 排序 = 收益/（风险×工作量）。CPU 收益按步进段自耗时占比折算；内存收益按 50M
外推。「语义透明」论证要点逐项给出；实施路落地时以对照测试（报告逐字节不变）为准。

### 低风险局部

| # | 选项 | 预估收益 | 风险 | 工作量 | 语义透明论证要点 |
|---|---|---|---|---|---|
| O1 | `takes_state` 结果缓存：装载点（`probe_pi32v2.upstream()` 返回后）为 per-model 缓存判定结果替换每次 effect() 的反射（codex 修正：**首次调用时缓存**优于装载期预计算——保留首次反射执行位置、不为未执行函数提前触发错误；按 callable 身份缓存） | CPU **~10-13%**（inspect 自耗时 13.8% 几乎全消） | 低（上游钉死文件不动，wrapper 在仓内装载点；不全局改 `inspect.signature`） | 小（~20 行+对照） | 函数签名按函数恒定，缓存结果与逐次反射**恒等** |
| O2 | 诊断行惰性化：主循环 `row.update(text=codec.format(...), bytes=mem.read().hex())` 改为只对保留窗（最后 64 行）内的行构造；`row['pc']`/`next_pc` 等廉价字段不变 | CPU **~15-17%**（format 族 6.4%+read/hex/row 开销） | 低-中：trace 最后 64 行进报告，须逐字节同形（对照测试钉） | 小-中 | 格式化是纯函数；丢弃行为已在发生（>64 行即 pop），只是把「先构造后丢弃」变「不构造」 |
| O5 | 簿记②聚合：deliveries/milestones 改计数+首末+具名片段 | 内存 MB 级；SNAP 快照 2.36MB→<0.2MB | 中（codex 收紧：**删除原报告暴露的完整列表=改报告契约**，重钉断言不证明兼容；抽样不能代替具名条目完整保留）——**延后** | 小-中 | 消费者只读计数/首末/具名条目时可精确聚合；须走报告契约显式变更而非静默重钉 |
| O3 | Memory.read 快路径：regions 预排序二分；RAM 区改字节数组段+初始化位图（保逐字节未初始化检测）；mmu/sfc/handles 前置判断合并 | CPU **~10-20%**（A 类 37.8% 的子集） | 中：Memory 语义=严格停的地基，改形态须保未初始化/未映射判定逐字节等价 | 中 | 对照=全场景报告逐字节不变+专门未初始化负例；bit-map 与 dict 装配在「哪些字节已知」上一一对应 |

### 结构性

| # | 选项 | 预估收益 | 风险 | 工作量 | 说明 |
|---|---|---|---|---|---|

## 6. codex 参谋结论（gpt-6-astra，2026-11-15，`~/tmp/codex-perf.log`，全文照录归档）

**主线裁决：O6 先解除内存限制（trace 从列表改可顺序读取的文件），O4 用于紧凑落盘
而非最终内存方案；O8/O7 各自独立过关等价性后再接入；三镜像加一项「轨迹生成一次、
两对复用」把六臂降三臂（不需要快照、不算 L2 快照化、不借用其豁免）。** 对用户原话
的直接回答（codex 原意）：16GB 主要花在保存数千万条 Python 轨迹对象上，双世界状态
按实测只有 ~40MB；CPU 主要花在访存框架、反射、诊断格式化和签名维护——现有证据不足
以支持重写指令语义核心。

采纳要点（逐条）：

1. **内存路线四步**：①trace 落盘（先双臂各自完整落盘、比较器顺序读，再演进到「A
   落盘、B 边跑边比」）；对照=落盘读回逐字段相等+新旧比较器报告逐字节相等+空轨迹/
   首/末分歧/Blocked/末尾未闭合分歧段边界+文件截断不得解释为 EOF+RSS 不再随行数线性
   增长。②O4 打包（`decode(encode(row))==row` 全语义、跨文件共享 intern 映射或读回
   同一语义值、不得因打包新增截断/拒绝）。③双臂**同步**流式需先证执行独立性（模块级
   计数器/缓存/intern 表/诊断全局态不得互相污染）；无隔离保证则文件方案证明面更小。
   ④三镜像轨迹复用：三份 pair 报告分别与原六次执行逐字节相等。
2. **O8 与 L2 挂账**：同一活世界分段交 trace 续跑=O6，不引入快照证明责任；真正销毁
   世界再恢复才引入 O8 证明责任；差分工具里先做证明**值得做但工具位置不降低证明
   要求**——必须逐臂证明「连续执行 vs 分段恢复报告逐字节相等」（两臂可能带同一恢复
   错误而差分仍通过），测试矩阵覆盖 advance-tier（全核 IDLE/masked pending/同刻事件/
   期限±1/Blocked 前后），过关后才关挂账接入 L2。**快照尺寸口径统一**：设计文档
   <0.5MB 是 3.17M 时代估算，21.8M 实际 ~2.36MB（timer0 簿记 2.2MB 大头）——预算用
   长程实际值。
3. **签名粒度：窗口采样在现行「逐步精确」声明下不可用**（反例：某寄存器第 10 步
   分歧、第 20 步恢复、PC 全程一致——64 步采样全漏）；采样只能声明「每步控制流一致+
   采样点签名一致」，是**削弱声明**。保持每步全签名语义的合法方向：直接比较规范化
   值延后串化/基值+精确变更记录/脏寄存器集合（须覆盖指令执行、中断、异常、复位、
   恢复全部写入口）。流式对比等价条件：同索引比较+计数+当前分歧段+固定上下文窗可
   精确流式；reconvergence 用候选起点+确认计数；跨臂 lag 重排需文件+索引承接；尾部
   显式 EOF（zip 短臂截断≠正常结束）；不得用消费速率不等的 tee 复用流。
4. **O1 认可但改首次调用缓存**（优于装载期预计算：保留首次反射的执行位置、不为未
   执行函数提前触发错误；按 callable 身份缓存、不全局改 `inspect.signature`）。
   **O2 收紧**：无法预知哪 64 行最终留下→保 64 条**不可变诊断材料**（输入对象），
   报告时才格式化；`mem.read()` 的 MMIO/副作用/Blocked 必须原位执行（只能推迟
   `.hex()`/格式化）；入队时机/失败指令是否入队保持。**O3 拆两次**：先查找路径
   （保字节 dict），再存储形态（字节数组+位图，按实际 RAM 段分配）；守住
   require→translate→SFC→region/MMIO→read 判定序、region 重叠优先级、未初始化≠零、
   部分访问副作用、别名/自修改/解码缓存失效/快照序列化；三层证据=访存级对照+边界与
   生成式对照+机器级报告逐字节+SNAP 回归。
5. **O7 现有三条件不充分**：「保守上限」须澄清为「已证安全批量边界 D（前 D-1 步
   无需逐步处理的事件）」；证明对象=状态相等**且有序事件/日志/统计/失败行为完全
   一致**；固定扫描序只解决同刻排序、masked pending 资格冻结≠内部状态冻结（计数器/
   pending/watchdog 仍走）；「批量后单步校验」只查边界不证中间无事件。ROI 上限也
   有限：事件时钟 11% 墙钟→最多 1.12x，S19 形状 25-30%→最多 1.33-1.43x。**裁决：
   当前阶段保留逐虚拟步，只做 advance() 内部已证重复计算的消除；闭式批量推迟到
   实验阶段逐状态域证明（另涉 BI 契约修订）。**
6. **预算目标线（工程目标非测量保证，按每臂 50M）**：单臂 ≤0.5GiB/≤45 分钟（后期
   ≤40）；双镜像 ≤1GiB/≤90 分钟；三镜像六臂 ≤1GiB/≤4.5 小时；**三镜像三臂（轨迹
   复用）≤1GiB/≤2.5 小时（后期 100-125 分钟）**。O1/O2/O3 合计按 25-40% 墙钟改善
   做规划区间（不可加）。
7. **O5 延后并收紧**：消费者只读计数/首末/具名条目时可精确聚合，但**抽样不能代替
   具名条目的完整保留；原报告若暴露完整列表，删除列表就是改报告契约**，重钉断言不
   证明兼容。**O9 暂不立项**（"10-50x"缺当前数据支持；将来必要时只替换经测量的少量
   热点、保 Python 外壳）。当前最有把握的收益=轨迹生命周期管理+重复计算消除+三镜像
   执行复用。

改动——整块 list dump/帧头/长度前缀——第一时间炸）；`test_trace_spool_
batched_write_truncation_matrix_raises_not_silent` 钉批量化后块界 ±1 与

### 12.2 W3-2 签名行 value→str memo

`_register_signature` 的 int 路径（每步 16 寄存器的 `f'{value:08x}'`）
加按值 memo：模块级 dict，值为 `sys.intern` 过的签名串（与 after_step
原有 intern 语义一致，同值命中**同一对象**，DT 快速相等路径不变）；bool
分支在前不受影响（bool 是 int 子类），UnknownWord/IcfgValue/兜底路径原样。
**纯函数无失效义务**（同一 int 的签名字符串恒定），只防无界增长：条目
上限 1<<16 超限全清（照 O3I 闭包 memo 先例，§8；20M 世界唯一串实测
33,364 ≪ 65,536）。单测两例：命中/矩阵（同值同对象、0/负数/满宽/超宽
格式化恒等、bool 不进 memo、Unknown/Icfg 输出逐字节不变）+ 上限淘汰
（cap 触发全清、清后重建键值照常正确）。

## 13. 三臂进程并行实施记录（路 PAR3 / sim-snapx，2026-11-16，一案一提交，基线 main 4178685）

三镜像条件轮的三个臂是**互相独立的仿真**（各自独立的 irq_case 世界，互不共享
状态），REUSE（§10）后仍串行执行（3 臂×~16 分钟 ≈50 分钟）。本路给
`tools/analyze_image_trace.py` 加 `--jobs N`（默认 1=原串行不变）：N>1 时
`RunPool.run_parallel` 用 fork 工作进程并发执行各镜像臂，每臂在子进程里跑与串行版
**完全同一**的 `frontier_run`（同 flag 集、同 PIN、同 monkeypatch——分叉副本各跑
各的），结束后把 result dict + 签名链 spool（O6 临时文件字节+chunk 索引）落
scratch 目录交给父进程；父进程以只读 spool 视图（`_ReadOnlySpool`：读路径继承
TraceSpool chunk 语义，append/flush 拒绝）接回 `pool.runs`，**比对仍单进程**在父
进程进行，消费矩阵（freshness+各 pair）不变。臂失败（子进程非零退出）以 require
显式失败，traceback 就地透传。

**值不变性论证**：每臂代码路径与串行版逐指令相同；子/父进程运行同一份代码，spool
handoff 是 run-local 约定非持久格式；单测钉死 fork handoff 后 result 逐字段相等、
spool 逐行相等（含 chunk 中随机读）。

**实测（本机 6 核，背景有其他路线负载）**：

| 场景 | 串行 | 并行 --jobs 3 | 报告对照 |
| --- | --- | --- | --- |
| crc_bankb 双镜像 --self-check | 29.6s | 20.5s（147% CPU） | **逐字节相同**（含 self-check 断言面） |
| p11 条件前沿三镜像（official/b79/l1_slotram，各 21.8M 步） | 68m33s（捕获轮，与 N-tier 等价验证并发） | **22m39s**（3.03x） | 剥离 top-level `snapshot_round` 溯源键后**逐字节相同**（捕获轮独有） |
| 同上 + `--resume-from`（SNAPX 快照轮） | — | **2.2s** | 停点/报告面与全量重放同值（轨迹面不重执行，见 docs/snapshot-resume.md） |

三臂并行 RSS=3×~130MB（O6 包络内）；串行基线本身受并发负载影响偏高，无负载纯串行
约 50 分钟（3×16），并行比恒为臂数比 3→1。
