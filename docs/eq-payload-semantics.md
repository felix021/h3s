## 1. 载荷 [0x60e3074,0x60e31c5) 逐段结构

0xe3074，运行地址 0x060e3074），337 字节，sha256 `f4e9501e…`（与 probe_pi32v2
`R2_PAYLOAD_SHA` 及修复候选镜像内字节三方一致 [镜像]）。**全部 102 条指令从
0x60e3074 起连续无洞解码到 0x60e31b2**（钉死 codec 逐条 decode 验证 [静态]），

### 1.1 fence 边界：为什么 r2 的 0x060c3338 错、修复的 0x060e31c5 对

debug_init 在 0x6034e92/0x6034e98 两条 `li.u32` 装 LIM_PC0 下/上限（下限
0x06000100 不变），0x6034e9e call RAM setter 0x12b7b8 写 LIM_PC0_L/H，0x6034eac
`00ef1000` 使能保护 [文档：eq-toggle/eq-fence-repair]。修复候选只改 0x6034e98 的
32 位立即数：官方/修复实测字节 `c1ff38330c06`（0x060c3338）→ `c1ffc5310e06`
（0x060e31c5），恰好 3 字节立即数差异 [镜像]。

- **0x060c3338 的原义**：原镜像代码/数据分界——原 SFC 应用明文区 [0x06000100,
  0x060e3053) 里，0x060c3338 起是 `.data` 初始化 blob（启动时复制到 RAM 0x124840
  [文档：eq-toggle]）与资源文件，可执行代码止于其前 [静态：AGENTS LIM 范围钉子]。
- **r2 为什么错**：EQ 镜像把可执行载荷放在资源区尾部 0x060e3074，5 个钩子的跳转/
  调用目标（0x60e3074/92/a0/b0/c2）全部 > 0x060c3338（首个目标超出旧上界 130,364
  字节）。任一钩子执行的第一条载荷取指即越界——不依赖端点策略细节。既有动态证据：
  probe_debug_startup 隔离回放中旧 r2 在 0x60e3092 被拒、修复候选执行 0x60e3096
  [文档：platform-startup]；probe_pi32v2 五个入口向量在旧 fence 下全 BLOCKED [文档]。
- **0x060e31c5 为什么对**（静态访问面论证）：钩子进入载荷后所有可能取指 PC 的最大值
  = 0x60e31b0（末条指令地址），指令完整边界 0x60e31b2。三种候选硅端点策略下修复值
  都充分：(a) 半开 PC<bound 且整条指令不跨界（模型现策略）需 bound ≥ 0x60e31b2；
  (b) 闭区间 PC≤bound 需 bound ≥ 0x60e31b0；(c) 更严的「PC+size≤bound 且再留量」
  同样被满足——0x060e31c5 比最小充分界 0x60e31b2 还多 19B 裕量，且恰为载荷（=整个
  应用明文区，载荷是最后一个文件）的末端，语义上等于「执行许可以镜像为限」[静态]。
  下限 0x06000100 保持原字节，载荷 ≥ 0x060e3074 远在其上 [镜像]。
- **既有 caveat 不变**：硅端点包含关系/低位处理未认证（eq-fence-repair.md），本节只
  给「载荷实际访问面」的静态证明；不构成刷机建议，候选维持 UNTESTED。

附注（并行槽读法）：vendor patch.asm 里 `r0 = -128 #` + 缩进的 `b[r0+0] = r3` 是
**同一 issue 的并行槽对**——store 用 issue 前 r0（=0x1265EA），新 r0=0xFFFFFF80 供
后续 `r5 = r0 & ~r1` 用。若按串行读会得出「向 0xFFFFFF80 野写」的错误结论；probe
既有 15 个编译用例的状态字节断言 + 本路 instrumented 写集（0x1265EA 翻转、无
0xFFFFFF80 写）已双重排除 [模拟器]。

### 2.2 修正：4/5 站点静态上就在 D1 事件循环分发可达集内

路 BR §3.3 断言「5 钩子函数簇全部调用者封闭（零 handler 命中）→ 全部不在 D1 事件
循环直接调用可达集内，全归音频效果域 D2+」。本路逐边复核发现该静态结论对 4 个站点
不成立（call 目标全部钉死 codec 验证 [静态]）：

1. **0x6025364 所在函数 0x60252c6 本身就是分发表 handler**：表 2（0x60a8c68，6×12B）
   记录[5] = {filter 0xff, event 0x10000c, handler **0x60252c6**}（LE 字于 0x60a8cac
   [镜像]）。BR 把该站点标为「fn 0x60251fc」——0x60251fc（模式切换）是其**前一个**
   函数、且恰被本 handler 调用（0x60254aa `call.l`→0x60251fc [静态]），疑似 BR 的
   函数边界把 handler 体并进了前函数，闭包因此漏掉这个入口。
2. **0x60059ce 所在函数 0x60057e6 被分发表 handler 直接调用**：表 1 记录[27]
   {0xff, 0x10000c, handler 0x6017e0c}，其内 0x6017ea4 `call.l -75458` → 0x60057e6
   （r0=15 实参；路径条件=事件 payload 字==53）[静态]。
3. **0x6025030 所在函数 0x6024fe6 被表 1 记录[42] handler 0x6023426 直接调用**
   （0x60237aa `call.l`→0x6024fe6 [静态]），并经「handler 0x60252c6 →(action 7)
   0x60251fc →(0x60252a4/0x60252b6)→ 0x6024fe6」链可达。
4. **0x602510e 所在函数 0x602503a** 经「handler 0x60252c6 → 0x60251fc →(0x60252a8)
   0x6025118（应用当前参数）→(0x60251f6)→ 0x602503a」可达 [静态]。

**正确的静态/动态分层表述** [codex 校订]：4 个站点（0x6025364/0x60059ce/0x6025030/
0x602510e）静态上位于以分发表 handler 为入口的可达集中；**「入口可达」≠「一次 handler
调用必经站点」**——每个站点还受 handler 内部分支条件约束（tbb 动作分发、事件 payload
字、当前模式/对象初始化状态；如 0x6017e0c 的调用边在 payload 字==53 的分支内、
0x60252c6 的站点在映射表命中点上）。D1 验收窗口内零命中应由该窗口的动态记录支持
（L2-a 的逐步签名正覆盖此事），而非再引「静态不可达」。0x6078846 仍 genuinely
D2：fn 0x60787ac 仅被 0x6078a40/0x6078b66（都在 fn 0x607898e=效果控制 handler 内）
调用，而 0x607898e 无任何静态调用者——它只能经效果节点 ops 分发到达（下节）[静态]。

对 L2 的影响：L2-a 设计不变（D1 窗口内零消费的动态结论照旧成立，解释从「结构不可达」
换成「窗口内未产生所须事件」）；L2-b P5/P6/P7 的引用改为「**指定 D1 场景及观测窗口内
零命中**」；P9 输入域决策点的分量上升（见 §4）。

### 2.3 ops 表 0x60a8ed0 调用面：节点框架与 0x6078846 的触发

效果注册表实测为 **28 条 24B 具名记录** [静态]（BR 记 27，差 1 不影响结论；8 组复用
同 ops 三元组）：{op0,op1,op2,name_ptr,uuid16,flags16}，[0x60a8ed0,0x60a9170)，
decoder/resample/…/**eq**/**wdrc**/dynamic_eq/…/encoder。要点：

- `'eq'` 记录 @0x60a8f78：ops={0x607857c,0x6078594,0x607863e}，**uuid16=0x737b**——
  BR 标作「u16 crc」的字段实为效果类型 UUID（0x737b 正是 eq-toggle.md 钉死的 EQ 节点
  UUID）。`'wdrc'` @0x60a8f90：ops={0x607876a,**0x607898e**,0x6078bb0}，uuid=0xdefe。
- **uuid 查找器 0x607452e**：从 0x60a8dec 起步 24 遍历到 0x60a917c，比较
  h[ptr+4]（=记录+16 的 uuid 字段），命中返回记录+12 指针；调用者 0x607471e/
  0x6074976（框架内部）[静态]。
- **节点构造器 0x6076b7a**：遍历另一张 **28B 步进注册表 [0x60a917c,0x60a9240)**
  （7 条，半字类型键@+0、create op@+4），命中后分配 48B 节点对象、`call [记录+4]`
  建效果私有句柄存 node+4 [静态]。0x60a9170..0x60a917c 12B 未解析（疑表头/哨兵）。
- **0x607538a（节点参数发送）是异步的**：打包 {uuid16, name[16], param[44]} 到
  1068B 消息、经 0x6074192 post 进框架消息队列（len<1025 时），不直接执行节点代码
  [静态]。也就是说 eq_toggle 的两条 SEND 只入队；bypass 字节真正落到 node+35 要等
  框架任务消费消息。
- **0x607898e（wdrc op1，控制 handler）** 的 subcommand 分发（tbh 表 @0x6078a1a，
  键=[包+0]-2）：**subcommand 2 → 0x6078a2e：`r0=b[包+4]; b[node+35]=r0`**——与
  eq_open_config 写的 ctx[35] 是同一字节（运行时 bypass）；值非 0 → call 0x607895c
  释放滤波资源，值 0 且句柄空 → 经 0x6078b60 call 0x60787ac 重开（即 0x6078846 的
  第二个入口）[静态]。
- 触发结论：**0x6078846 的两个入口都活在效果框架域**——(a) 音频流水线建节点时的
  open（op0 路径/构造器），(b) 控制消息 subcommand 2 置 0 重开。最小触发域=D2 音频
  首场景（首个音频事件 handler + 效果节点框架跑起来）。EQ 镜像与 b79 在此域的差 =
  「EQ 关时 MusicEqBt/Eq0Media 节点 ctx[35] 被强制 1」+「双击后两条 subcommand-2
  消息被入队」。

## 3. 状态字节 0x1265EA 与 &0x7F 掩码语义

字节布局（patch.c + 编译字节互证 [静态]）：bit7 = OFF_FLAG（1=EQ 关），bit0/bit1 =
源（1=自定义、2=预设），bit2..6 原镜像未用（保持 0）。上电 BSS 清零 → 默认
0x00 = EQ 开、无源记录。

**原镜像访问面复核** [静态]：全 app 扫描 `+42` 字节访问并核对基址来源——QCY 基
（0x1265c0 立即数 1348 处装载中）偏移 +42 的**读点恰 1 个**（0x60059ce，消费分支
0x60059d4 `if (r1!=2)` / 0x60059e2 `if (r1!=1)`）、**写点恰 2 个**（0x6025032=2、
0x6025110=1）；另 3 处 `b[..+42]` 命中（0x602da2c/0x602e532/0x6038d9c）基址均为
表解引用/调用返回的对象指针，非 QCY——eq-toggle.md「一个读取位置及两个写入位置均
被处理」成立。QCY[43]（预设 index）读 0x60059da/写 0x602502c 也在同一对函数内，
不承载标志位故无需掩码。

**掩码桩的实际效果**：

1. **读掩码（0x60e3092 桩）**：把 bit7 剥掉后原消费代码看到 1/2，行为与 b79 完全
   一致。若不掩（EQ 关时字节=0x81/0x82）：0x60059d4 `r1!=2` 成立 → r2=0（预设
   index 丢失，b[r8+1]=0）、0x60059e2 `r1!=1` 成立 → 自定义路径跳过——源选择会
   永远落入「既非 1 也非 2」的默认分支。**该掩码是 EQ 关态正确性的必要条件，不是
   观测增强**。
2. **写保持（record 桩 `&0xFFFFFF80`）**：记 source=1/2 时保留 bit7——EQ 关着换曲
   线/重装预设不丢「关」状态。
3. **toggle 位翻转（eq_toggle `insert(r2,p:0,l:7)`）**：只翻 bit7、低 7 位原样保留
   ——源记录在开关往复中不丢。
4. **open 符号读（eq_open_config `r1=b[..](s); ifs (r1>-1)`）**：符号扩展后
   bit7=1 → 负数 → 进入名字匹配强制分支；bit7=0 → 非负 → 跳过，bypass 完全按文件
   配置（与 b79 语义一致）。
5. **类型守卫**：eq_toggle 先读 QCY[5356]（0x127AAC，App EQ 类型），==10（空间音效
   独立路径）直接返回 0 且**零写入**——与原固件 fn 0x6025118 自己的
   `b[QCY+5356]==10 → 早退`守卫（0x6025124..0x602512e）同语义 [静态]。

**eq_toggle 完整行为** [模拟器 instrumented，输入/写集逐项]（与 probe 既有 3 个
toggle 编译用例互证）：

| 入态 | 动作 | SEND×2 内容 | RESTORE | 出态 | 返回 |
|---|---|---|---|---|---|
| 0x01（开） | 翻为关 | (2,1,0×9) 给 MusicEqBt/Eq0Media | 不调 | 0x81 | 1 |
| 0x81（关） | 翻为开 | (2,0,0×9) | **调 0x602619a(0,10)** | 0x01 | 2 |
| 任意,type=10 | 不动 | 无 | 无 | 原样 | 0 |

44B 命令包布局与原 ABI 完全一致：u32 subcommand=2 @+0、u32 bypass 值 @+4、余 0——
这正是原自定义应用循环（0x60250f8 同参数形：uuid 0x737b、name、44B、0x607538a）
与原控制 handler 0x607898e subcommand 2 消费的格式 [静态]。RESTORE 只在「翻为开」
时调（重开滤波器可能装载出厂参数，需回调恢复当前模式曲线——patch.c 注释）。

## 4. 对 EQ 修复离线验证的启示

目标回顾：修复候选 67ba97ef UNTESTED；离线验证 = 在仿真里证明「修复镜像的钩子/载荷
执行面与设计一致、且不引入 b79 之外的行为差」。按成熟度分层：

**现在就能离线做（静态+函数级，本路已补齐/已有）**：

1. fence 充分性静态证明（§1.1）：载荷访问面 vs 边界值，三种端点策略下 0x060e31c5
   均充分、0x060c3338 均拒绝全部五入口——这是「修复候选边界对」的最强静态证据。
2. 函数级语义回放：probe_pi32v2 15 个编译用例（8 source/3 toggle/4 node-open）+
   本路 instrumented 写集（§3 表、§1 访问面）——载荷每个函数的寄存器/RAM/API 形状
   已钉死；callee-saved 寄存器与栈保持已被既有断言覆盖。
3. 钩子等价性静态核对（§2.1 表）：每个 6B 窗口替换前后的原语重放关系（重放哪些原
   指令、丢哪些、语义差何在）已逐站点列明。
4. 三镜像差异游程复核（§6 镜像字节锚点）：b79↔修复候选恰 = 5 站点 + fence 立即数 +
   config.dat index/CRC + 追加载荷，无其他差异。

**事件注入场景即可着手（不需要 D2 音频流）**：连续启动上下文 + 经真实事件 post/
分发路径注入合成事件（显式 opt-in fixture——正是 BR §3.5 留下的 P9 决策点，本路证据
使其分量上升）。**不承诺一次按键覆盖全部** [codex]：按键路径直接关联 0x6025364/
0x6025030/0x602510e 三站（且不同动作/模式状态可能各走不同分支）；0x60059ce 的事件
语义未钉死，注入什么事件才能覆盖它是场景设计的一部分。可观测断言与边界 [codex]：

(a) 0x6025364 钩子在映射命中点执行、passthrough 路径寄存器等价——**站点执行覆盖
    要逐站点记录**（状态翻转/入队只证明写路径执行，不能替代各站点自身的执行证据）；
(b) eq_toggle 翻转 0x1265EA、两次调用 0x607538a——观测点放**实际入队边界**
    （0x6074192 post 的返回值与消息内容；仅命中 0x607538a 入口≠入队成功；入队还
    可能唤醒消费者，消费行为归 D2 侧观测）；
(c) RESTORE(0,10) 在调用者上下文同步执行（同步**调用**≠全部效果同步完成——其下游
    是否再投递消息/依赖音频对象，逐调用核对）；其链路会进 0x6024fe6/0x602503a →
    顺带覆盖两个 record 桩与 ROM 配置 API 读（需 ROM 在模型里，已有）；
(d) 再双击翻回，状态字节往返 0x01↔0x81。
这相当于把「修复镜像在连续启动上下文里执行载荷」验证到**控制面**；它证明钩子/载荷/
状态机正确，**不**证明音效链行为（bypass 是否落到节点上）。「SEND 消息尚未由消费者
执行节点更新」是该场景的诚实收口语 [codex]。

**必须 D2 音频首场景**：效果节点状态对比。断言形状 = EQ 关状态下开音频流 →
MusicEqBt/Eq0Media 节点 ctx[35]==1（b79 为文件配置值）、其他节点（EscoDlEq 等）
不受影响；双击后框架消费两条 subcommand-2 消息 → node+35 翻转 + 0x60787ac 重开
路径执行（0x6078846 钩子在此显形）。这是唯一能把「EQ 行为差」钉到节点状态的验证，
依赖效果框架任务（ops 表分发 + 消息队列消费）跑起来。

**诚实边界**：以上全部是投影/模型证据；硅端点策略、真实 DSP/RTOS 行为未认证；
本页不构成刷机建议，候选 UNTESTED 状态不变。

## 5. 不确定处（如实标注）

- handler 0x6017e0c 的 payload==53 事件、handler 0x6023426 的事件内容语义未钉死
  ——**不能排除启动/定时器等内部事件源**，故 §2.4 对 0x60059ce/0x6025030 保守表述
  [codex]；分发表 filter 字段（0xff/0x01/0x00）语义仍如 BR 未钉。
- 分发表匹配语义（record.event_id 与事件字的精确匹配规则、两表遍历顺序、先行
  handler 返回值是否截断后续分发、0x10000c 特路 0x60108fe 的再分发）未逐指令钉死；
  匹配语义只会收窄「哪类事件能走通路径」，**不会恢复 BR 的笼统不可达结论**（表内
  handler 值 + handler 体内调用链已钉）[codex]。
- 入口可达≠一次调用必经站点：0x60252c6 的 tbb 动作分发/映射命中、0x6017e0c 的
  payload==53、0x6023426 的事件分支、0x60251fc 的模式分支等路径条件未逐条钉死——
  注入场景要逐站点确认所需事件与前置状态，不能预设一次按键覆盖多站 [codex]。
- BR 闭包漏边的根因（函数边界误并 vs call 边提取缺陷）未定论；本路只钉「这 4 条
  边存在且被 codec 验证」。BR 的 26,785 边提取方法与本路 17,586 直接调用边（4B
  call.l 9,128 + 6B call.xl 8,458）口径不同，不能直接对比。**流程改进 [codex]**：
  后续静态可达性分析应把两张分发表的全部 handler 自动纳入调用图入口，并对每个
  关注站点输出「入口→站点」路径及未证明的分支条件，使「调用者封闭」类结论可复查。
- ops 表 0x60a9170..0x60a917c 12 字节、28B 注册表 [0x60a917c,0x60a9240) 各记录的
  类型键语义未解析；'eq' 记录 op1（0x6078594）与 'wdrc' op1（0x607898e）谁最终
  消费 0x737b 消息取决于框架 uuid→ops 解析细节，未逐层追完（对结论无影响：payload
  的 SEND 与原应用循环 0x60250f8 调用形完全一致，路由行为同 b79）。
- L2-a 场景转录/freshness 钉子仍以 BJ 落地时的 main 为准（同 BR caveat）。
