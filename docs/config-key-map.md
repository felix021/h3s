# 配置 key 1..99 占用枚举 + 空 key 选型（R4 后续，路 K/sim-keyenum）

只读调研。基线 main `3bcf56e`。本文把路 CR 的「待补 doc §5」第一项（key 1..99 全语义枚举）落地，并回答「声道平衡是否存在」+「挑哪些空 key 给自定义配置」。

一句话结论：**key 1..99 里 45 个已占用（16/42/22/20/48/101 等能钉死或强推断语义，其余有长度和 RAM 落点但语义待命名）、54 个空（没有任何 getter/setter 引用）；「声道平衡」没有专用 key（App 面板有该项但没有绑定命令，固件里 key 6 是 3×float32 但语义未钉死是左右声道）；自定义配置挑 30/31/32 三个连续空 key，新 key 只需「约定 key 号 + 读写字节格式」，无需在任何地方注册长度/默认值。**

> 反汇编基址 0x06000100，官方原 app.bin SHA256 `18f3d573…`。证据等级：`[静态]`＝反汇编/镜像直接钉死；`[推断]`＝按长度/面板/行为对照的合理推断；「待命名」＝观察到了读写但语义不明。函数名是行为命名，非恢复符号。

## 1. 方法

从两个入口出发穷举：

1. **VM 后端**：`get_config 0x06000f88` / `set_config 0x06001f12` 是 VM 区（key 1..99）唯一的读写入口（VM 后端 match `0x06061304` 判定 `key-1<256`；get `0x06060ea0`/set `0x06060efe` 全 app 只被分派器以 key=255 调起＝提交 VM 头，没有任何旁路直接用数据 key 调后端）。
2. **syscfg 成批读 `0x0601194e` 一带**（开机加载 QCY 全局结构 `0x1265c0` 与音频框架 `0x1249bc` 的主路径），逐项是「内联 `r0=<key>` 后接 call get_config」，不是表驱动。

做法：把整份线性反汇编（306k 行）解析成指令流，解析每个 `call`（目标＝指令尾 + 带符号位移，AGENTS 不变量 5），筛出目标＝get_config/set_config 的调用点，再反向追踪 `r0` 寄存器取 key 立即数。共 73 个 get 点 + 80 个 set 点。有 4 处 key 是动态的（非立即数），逐个追过：`0x60095d0` 是透传包装（其调用者 key=45 和描述符表 key 字节）、`0x60425ce`/`0x6044996` 是 key=118+r4（118..127，超出 1..99）、`0x6061440` 读表（key 819/820，超出 1..99）。

另有一张「配置描述符链表」walker（`0x60097fe`，key 取描述符 `[+13]` 单字节）：它只被函数指针间接调起，全 app 无直接 call；其 4 个注册桩（`0x600ec2e/ecc6/ed30/edfa`，分别注册 0x1248b2/eb/05/3e 四个描述符）各自用 set_config 写 key **101/46/44/45**——全部落在直接枚举已覆盖的集合里，**不新增 1..99 的 key**。因此直接枚举结果＝完整占用集合。

## 4. 声道平衡是否存在

**结论：没有专用 key，需要新增。**

证据：

- [静态] App 控制面板 `data/controlpanel_qcyh3s_16764.json` 里有「声道平衡」项，但 `type=8`，**没有 `cmdid`/`id`/`hasValue`**，info 还是从降噪模式复制过来的占位文案——即 App UI 有个占位入口，但没有任何下发命令绑定。
- [静态] 固件侧 1..99 里没有 2 元素的 L/R 平衡 key。最接近的是 **key 6**（12B＝3×float32，默认全 1.0f，落在 `0x1265c0+4488`）：3 个 float 不等于左右两声道，且消费点语义未钉死，不能断言是声道平衡。
- 因此「声道平衡」＝**无（需新增）**：挑一个空 key 存 L/R 增益（如 2×float32 或 2×i16），App 侧新增一条自定义命令下发，固件侧 setter 写 key + 生效逻辑自己实现。

## 5. 空 key 选型建议

54 个空 key 里挑连续、好记、落在干净大段的：**推荐 30/31/32**（或备选 70/71/72）。

理由：

- **空**：27..36 整段 10 个 key 全部无任何 get/set 引用（描述符链表也不含），30/31/32 在其中间，前后各留了缓冲（27/28/29、33/34/35/36），即便将来固件在相邻号加配置也不容易撞。
- **VM 区可写**：key 1..256 全部命中 VM 后端 match（`key-1<256`），30/31/32 天然走 VM 区（Flash 0x1da000、双半区磨损均衡、RAM 位图 0x1272ac），可读可写可持久化。
- **无冲突**：不在已占用的 45 个 key 里；也不和「面板 cmdid 号」冲突（面板 cmdid 20/25/29/31/46 对应的是另一套命令号，与存储 key 号空间独立）。
- **约定即用**：选 30 存声道平衡（如 2×i16 或 2×float32）、31/32 留给后续配置，读写字节能自己定。

## 6. 新增自定义 key 的最小路径（如声道平衡）

**核心结论：新 key 只需「约定 key 号 + 读写字节格式」，不用在任何地方注册长度/默认值。** 因为 VM 后端 match 是 `key-1<256`（对 key 1..256 一律命中），get/set 都不校验「这个 key 有没有注册过」；长度上限只有一条 `len≤4095`（VM set 校验 `0x06060f0e`）。默认值不是注册出来的，是**你自己的开机 init 里写的**（照抄 key16 的 `0x0600dddc` 模式）。

固件侧要做的两件事：

1. **写（生效 + 持久化）**：在命令 setter 里 `set_config(30, buf, len)`（或调 `0x06001f12`）。落地 Flash 是同步的（写缓冲→更新位图→VM 头 key255 提交，路 CR 钉死）。
2. **读（重启加载）**：开机 init 里 `get_config(30, buf, len)`，然后按「读回长度 != 期望长度 → 用内置默认值」回退（照抄 `0x0600dddc` 的 `if (r0 != 3)` 分支）。这样新 key 首次上电没数据时自动落默认。

App 侧要做的：

1. 仿命令 0x17/0x22 注册一条**新的 BLE 自定义命令**（QCY A002/1 write，RCSP `FE DC BA|C0|FF|cmdid|len_BE16|body|EF`，见 docs/app-protocol.md），例如拿一个新 cmdid 下发 `[声道平衡 L/R 字节]`。
2. 复用 android-query 既有传输层 + WritePolicy 白名单思路，只放行形状匹配的新 setter 帧，不开任意字节写总开关。

不是「复用 get_config/set_config 还要注册」二选一——**就是纯约定**，因为 key 1..256 的 match/get/set 全在分派器里现成，没有任何 per-key 注册表要改。

> 注意：持久化只解决「存值」，声道平衡要真正生效还得自己写消费逻辑（把读回的 L/R 增益喂进 DSP/音频框架），和「按键功能」那种要改按键分发表的坑同款（docs/runtime-persistence.md §4.3）。

## 8. key 30 读写演示（路 AB/sim-keydemo，函数级仿真）

「空 key 只需约定 key 号+字节格式」的结论已在函数级仿真里落地验证（2026-11-14，基线 main `1975ff8`）：opt-in 场景 `--vm-key-scene`（probe_pi32v2）直调真实 get_config/set_config 分派器，在空白 VM 区上 **set_config(30, 8B) 全链真实执行（CRC/窗口写/偏移表/位图/key-255 头提交）→ 同机与「重启世界」（真实 vm_init 重扫记录链）读回均逐字节一致**；对照组已占用 key 16（降噪 3B）在重启世界原样读回 `01 01 02`；flash 写侧（SFC 擦写）在半区写满触发磨损均衡换区时真实推进到 0x12cc40 并诚实停在未建模 MMIO 读。VM 记录格式 `{u8 crc, u8 key, u16le len<<4}+data`、半区头 magic、key→偏移表 0x129088 等结构细节一并钉死。详见 [docs/vm-key-roundtrip.md](vm-key-roundtrip.md)（含 App 侧「写 key 30」最小对接路径与诚实边界）。
