# 模式键两态循环：实际固件证据和补丁

## 目标与结果

让当前用于降噪切换的物理按键只在ANC ON和通透间往返，跳过OFF。当前发布包已实际写入，用户确认达到预期。开机默认状态、App模式选择入口、EQ和ANC滤波器不属于这次按键改动。

这个结论来自三层证据：QCY App命令解释、H3S自己的机器码与常量表、实际OTA和用户操作反馈。参考SDK用于核对结构和语义，没有被当成QCY确切源码。

## 模式编号先分清

| 语义 | QCY线协议 | 固件内部ANC编号 | 通用杰理VoiceMode编号 |
| --- | ---: | ---: | ---: |
| 正常／OFF | 2 | 1 | 0 |
| 降噪／ON | 1 | 2 | 1 |
| 通透／TRANS | 3 | 3 | 2 |

固件app.bin+0x9E17D有三对映射字节 `01 02 02 01 03 03`。`0x060189AA`附近的实际代码用映射把内部模式转为QCY状态；App直接设置路径在 `0x0600DCEE` 把QCY模式分派为内部ON2/OFF1/TRANS3。这些编号差异是为什么不能把通用接口中的 `mask=6` 直接当成固件内部mask。

## 从字符串到处理函数

原app.bin摘要：

```text
18f3d573a5b1a15f488a6803ce4f828634e602015c85e92d205bbe62d7060041
```

1. app.bin+0x9CE4F的 `anc_next` 字符串，运行地址0x0609CF4F。
2. 0x06018CC6加载该字符串，所在命名按键处理器从0x06018CC0开始。
3. 处理器在0x06018CE8调用0x06018B60。完整函数还处理设备状态／同步条件，不是发现一个字符串就推断补丁。
4. 0x06018B86把表地址0x0609E510加载到r4。
5. 例程读取三项表、当前内部模式和mode_enable，再在0x06018BE0调用模式应用包装0x060189AA。

`tools/analyze_anc_cycle.py` 找到五个对0x06018B60的直接调用位置：

```text
0x06018BF0  0x06018CE8  0x060235DE  0x0602548C  0x0606E576
```

原app中表地址的直接32位常量只出现于app+0x18A88，即那条加载指令的立即数部分。直接指针搜索不能数学证明没有计算出来的别名；因此后面还进行了实际行为验收。

## 函数实际做了什么

与选择下一模式有关的伪代码如下。训练状态保护、IRQ锁和淡入设置省略，决定下一索引的分支全部保留：

```c
next = 0;
for (i = 0; i < 3; ++i) {
    if (table[i] != current_mode) continue;
    next = i + 1;
    if (next >= 3) next = 0;
    if (!(mode_enable & (1 << table[next]))) {
        ++next;
        if (next >= 3) next = 0;
    }
    break;                 // 第一次匹配后停止
}
apply_mode(table[next]);
```

证据不是编译参考SDK得到的相似函数，而是 [原固件函数片段](../evidence/anc-cycle/06018b60-06018be6.asm)。人工还原的完整说明在 [key-cycle-reconstructed.c](../evidence/anc-cycle/key-cycle-reconstructed.c)。这些是分析伪代码，不能被描述成恢复了原始符号或完整C源码。

pi32v2的相对call/jump以**该条指令结束位置**为基准。工具打印的 `call -396` 不能直接用当前指令起点相加。比如0x06018CE8的4字节call：`0x06018CE8 +4 -396 =0x06018B60`。

## 为什么改成02 03 02

原表是 `[OFF1, TRANS3, ON2]`。把首项OFF1改为ON2，得到 `[ON2, TRANS3, ON2]`。由于第一次匹配后停止：

| 当前状态 | 原表下一状态 | 新表下一状态 |
| --- | --- | --- |
| ON2 | OFF1 | TRANS3（先匹配索引0） |
| TRANS3 | ON2 | ON2（索引1→2） |
| OFF1 | TRANS3 | ON2（没找到当前项，默认索引0） |
| 未识别的模式 | OFF1 | ON2 |

因此重复ON并不产生“降噪→降噪”的额外一档；它依赖这里已确认的first-match语义。也不用改循环项数、分支指令或mask初始化。

分析程序对所有仍启用内部ON2／TRANS3的mask，以及0/1/2/3/255五种初态，各推演100次，均只在ON／TRANS交替。模拟证明的是还原算法的结果，硬件验收来自后续用户确认。

## 精确差分和打包

- 原表运行地址0x0609E510，app偏移0x9E410，uFW位置0xA0B30。
- 修改 `01→02`，机器指令字节不变。
- 当前app摘要 `8f594d5908f6d4eac9b63e5e4538d3c0dbf0ed1a1e285547fcf2d9c6b0914517`。
- 相对已刷的仅提示音包，app只有1个表字节变化；uFW变化20字节，另外19字节是app子层、父层、总体头及外层CRC元数据。
- 原有提示音参数保留。ANC系数、提示音音频内容、引导程序、版本号和外层其他资源不变。

生成器校验原包、原app摘要、原表、加载指令和原始CRC后才修改。独立解包又确认app只变化这一字节。详见 [差分报告](../evidence/delta-verification.json) 和 [复现检查](../evidence/publication-reproduction.json)。

## App正常模式为何保留

QCY「声音」页不是调用这个next函数，而是发送明确的模式／场景／强度，进入命令0x17的直接设置路径。因此补丁只改变“下一档怎么选”，不删除OFF实现，也不把App所有OFF设置改写成ON。源码路径和固件分派见 [App分析](app-analysis.md)。

本轮未单独要求用户回归测试App的正常模式入口，应该称“该路径未改”，而不是“所有App功能已全测”。同样，不能由这一补丁推断开机默认ANC已经修改。
